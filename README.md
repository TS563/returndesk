# ReturnDesk

A returns desk for a small online store. Support agents raise return/replacement requests, work them through a fixed lifecycle (review → approve or reject → complete), decide on a refund, replacement or store credit, leave notes, and close requests out.

**Live app:** https://returndesk2.netlify.app/
**Repository:** https://github.com/TS563/returndesk

---

## Features

- Raise a request with customer, order, item, quantity and reason. The reference (`RD-000042`) is generated by the system.
- Find requests fast: search by customer, order or reference, filter by status and reason, sort, and page, all combined and all done in SQL.
- Work a request: full detail view, append-only notes, status transitions, edit details while undecided, remove (soft delete).
- Status shown as a coloured badge with a text label; only the actions that are legal for the current state are offered.
- Loading, empty and error states everywhere; server refusals are shown to the user with the server's own explanation.
- Responsive down to 375px (table on desktop, cards on mobile).

## Business rules and where they are enforced

Every rule is enforced on the server; the UI only mirrors them.

| Rule | Application code | Database |
|---|---|---|
| 1. Status flow (Open → In Review → Approved → Completed, or In Review → Rejected; final states are final) | `lib/rules.js` → `assertTransition` (409 `INVALID_TRANSITION`) | |
| 2. Approval needs a resolution; refund needs an amount > 0; no amount otherwise | `lib/rules.js` → `decisionFields` (422 `VALIDATION_ERROR`) | `CHECK` constraints `resolution_matches_status`, `refund_amount_rules` |
| 3. One live request per order + item | Unique violation translated to 409 `DUPLICATE_LIVE_REQUEST` | Partial unique index `uniq_live_request_per_order_item` |
| 4. Locked once Approved / Rejected / Completed | `lib/rules.js` → `assertEditable` (409 `REQUEST_LOCKED`) | |
| 5. Removal never destroys the record; only Open or Rejected | `lib/rules.js` → `assertRemovable` (409 `CANNOT_REMOVE`); soft delete via `deleted_at` | |

## Design decisions

- **Partial unique index for rule 3** instead of check-then-insert, which has a race condition. The database refuses the duplicate even for concurrent requests.
- **Transitions use `SELECT … FOR UPDATE` inside a transaction**, so two agents cannot move the same request at the same time.
- **Rules are pure functions** in `lib/rules.js`, separate from SQL (`lib/repository.js`) and from HTTP (route handlers), so validation logic lives in one place.
- **Constraints are duplicated deliberately in the database** (CHECKs, partial index, append-only trigger on notes) as a second line of defence.
- **The API tells the UI what is legal.** Each request includes `actions: { transitions, can_edit, can_delete }`, computed by the same rules code, so the UI cannot drift from the server.
- **Soft delete** (`deleted_at`): removed rows stay in the table, return 404 from the API, and stop blocking new requests for the same item.
- **Notes are append-only**: no edit/delete endpoints and a database trigger that rejects `UPDATE`/`DELETE`.
- **Server-side search/filter/sort/paging** in one parameterised query. Sort columns come from a whitelist; `LIKE` wildcards in the search term are escaped. A separate `count(*)` provides the total.
- **References** come from a Postgres sequence default, so they are unique and never typed by a person.
- **Consistent errors**: `{ "error": { "code", "message", "details" } }` with 400 (bad JSON), 404, 409 (state/duplicate conflicts), 422 (validation) and 500 (unexpected). Unknown API paths return JSON 404.
- **Search is debounced** (400 ms) and in-flight requests are aborted when a newer one starts.

## Data model

`return_requests`: `id` (uuid), `reference` (unique), customer name/email/phone, `order_number`, `item_sku`, `item_name`, `quantity`, `reason`, `status`, `resolution`, `refund_amount numeric(10,2)`, `deleted_at`, timestamps.
`request_notes`: `id`, `request_id` (FK), `body`, `author`, `created_at`. Append-only.
Full DDL: [`db/schema.sql`](db/schema.sql).

## API

All responses are JSON. Success: `{ "data": … }` (lists add `"meta"`). Failure: `{ "error": … }`.

| Method | Path | Description |
|---|---|---|
| GET | `/api/requests?q=&status=&reason=&sort=&order=&page=&pageSize=` | Search, filter, sort, page |
| POST | `/api/requests` | Create (201). 409 if a live request exists for that order + item |
| GET | `/api/requests/:id` | Detail including notes, oldest first |
| PATCH | `/api/requests/:id` | Edit details. 409 `REQUEST_LOCKED` once decided |
| POST | `/api/requests/:id/transition` | `{ "status", "resolution?", "refund_amount?" }` |
| DELETE | `/api/requests/:id` | Soft delete (204). Only Open or Rejected |
| POST | `/api/requests/:id/notes` | Add a note (201). Allowed in every status |

Example refusal:

```json
{
  "error": {
    "code": "INVALID_TRANSITION",
    "message": "A request cannot move from Open to Completed.",
    "details": { "from": "OPEN", "to": "COMPLETED", "allowed": ["IN_REVIEW"] }
  }
}
```

## Running locally

Requires Node 20.6+ and a PostgreSQL database (a free [Neon](https://neon.tech) project works well).

```bash
git clone <GITHUB_REPO_URL>
cd returndesk
npm install
cp .env.example .env        # set DATABASE_URL (Windows: copy .env.example .env)
npm run db:seed             # creates the schema and loads demo data
npm run dev                 # http://localhost:3000
```

Local Postgres with Docker, if you prefer:

```bash
docker run --name returndesk-db -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=returndesk -p 5432:5432 -d postgres:16
# DATABASE_URL=postgres://postgres:postgres@localhost:5432/returndesk
```

| Script | What it does |
|---|---|
| `npm run db:migrate` | Applies `db/schema.sql` only (idempotent) |
| `npm run db:seed` | Applies the schema, **wipes the ReturnDesk tables**, then inserts 37 requests across every status and reason, with notes |
| `npm run dev` / `build` / `start` | Standard Next.js scripts |

## Assumptions

- No orders/customers/products tables are specified, so order number, item SKU/name and customer details are stored on the request.
- Rejected is reachable only from In Review, as drawn in the brief's diagram.
- "Not yet decided" (editable) means Open or In Review.
- The duplicate check is per order + item SKU (case- and whitespace-insensitive), regardless of customer.
- Currency is displayed as INR.
- There is no authentication (not in the brief); notes default to the author "Agent".
